# Performance benchmark

This page reports what was **measured** on one machine. It is an indication of the order of
magnitude for files of about 100,000 rows, not a guarantee for other machines, other files
or larger sizes.

## Summary

Final code (version 0.1.0 as published), 100,000 data rows per file, three measured runs
each after one warm-up run:

| Workflow | Median wall-clock time | Range (3 runs) | Peak working set (RAM) | Peak committed memory |
| --- | --- | --- | --- | --- |
| Customers, CSV → CSV | **31.96 s** | 31.88 – 33.07 s | **331.8 MiB** | 663.3 MiB |
| Orders, XLSX → XLSX | **125.64 s** | 119.37 – 126.27 s | **517.4 MiB** | 848.7 MiB |

All six runs produced outputs that passed an independent verification (1,032 checks per
customers run, 1,031 per orders run, 0 failures), and the input files were unchanged.

## Datasets

Generated by [`scripts/benchmark/generate_data.py`](../scripts/benchmark/generate_data.py)
with the fixed seed `20261013`; the same command always produces the same rows (the CSV is
byte-identical; the `.xlsx` has identical cell content, while its bytes contain a save
timestamp). The schemas and configurations are those of the repository samples.

| | Customers | Orders |
| --- | --- | --- |
| File | `customers_100k.csv`, 8,529,574 bytes | `orders_100k.xlsx` (sheet `Orders`), about 4.1 MB |
| Shape | 100,000 rows × 8 columns | 100,000 rows × 7 columns |
| Configuration | [`config/customers_config.json`](../config/customers_config.json) (10 validation rules) | [`config/orders_config.json`](../config/orders_config.json) (5 validation rules) |
| Injected problems (examples) | 1,000 exact duplicates, 489 key duplicates, 4,927 ambiguous dates, 1,890 unparseable amounts, 5,981 missing amounts, 994 invalid statuses, 497 missing IDs | 1,000 exact duplicates, 300 key duplicates, 2,871 unconvertible dates, 2,936 customer IDs stored as numbers, 3,061 invalid quantities, 989 rows to quarantine |
| Expected result | 97,509 cleaned, 1,000 removed, 1,491 quarantined | 98,011 cleaned, 1,000 removed, 989 quarantined |

Expected results come from the generator's own record of what it injected
(`manifest.json`), not from the toolkit.

## Method

- **Commands**, run by [`scripts/benchmark/run_benchmark.py`](../scripts/benchmark/run_benchmark.py)
  in the order warm-up (both workflows), then customers 1, orders 1, customers 2, ...:

  ```text
  data-clean clean data/customers_100k.csv runs/customers/runN/customers_clean.csv --config config/customers_config.json
  data-clean clean data/orders_100k.xlsx runs/orders/runN/orders_clean.xlsx --sheet Orders --config config/orders_config.json
  ```

- **Time:** `time.perf_counter()` from process creation to exit. It includes interpreter
  start-up, reading, profiling (twice), cleaning, validation, writing and re-reading every
  output for verification, and writing both reports. No per-phase breakdown was measured.
- **Memory:** the command is started suspended inside a Windows Job Object, so the
  `data-clean.exe` launcher and the Python processes it starts are all included
  ([`measure.py`](../scripts/benchmark/measure.py)).
  - *Peak working set:* the largest `PeakWorkingSetSize` (physical memory) of any process
    in the job, read with `GetProcessMemoryInfo`.
  - *Peak committed memory:* `PeakProcessMemoryUsed` of the job, maintained by the kernel
    (private memory that Windows had to guarantee; it includes reserved memory never
    touched, so it is higher than the working set and is the cautious figure for sizing).
- **Calibration:** before the runs, processes that allocate 200 MiB, 800 MiB and (through a
  `cmd.exe` launcher) 500 MiB were measured at 206.2 / 807.8 / 506.9 MiB committed and
  211.9 / 812.1 / 512.0 MiB working set, i.e. within the size of the Python interpreter.

## Results: final code

| Workflow | Run | Exit code | Time (s) | Peak working set (MiB) | Peak committed, largest process (MiB) | Peak committed, whole job (MiB) |
| --- | --- | --- | --- | --- | --- | --- |
| customers | warm-up (excluded) | 3 | 57.72 | 331.8 | 663.0 | – |
| orders | warm-up (excluded) | 3 | 132.43 | 517.3 | 849.2 | – |
| customers | 1 | 3 | 33.07 | 331.8 | 663.0 | 664.6 |
| orders | 1 | 3 | 119.37 | 517.6 | 848.7 | 850.3 |
| customers | 2 | 3 | 31.96 | 331.8 | 663.3 | 664.9 |
| orders | 2 | 3 | 125.64 | 517.4 | 848.6 | 850.2 |
| customers | 3 | 3 | 31.88 | 333.0 | 664.5 | 666.2 |
| orders | 3 | 3 | 126.27 | 517.4 | 848.7 | 850.2 |

Exit code 3 is expected: the runs succeed, and the data contains the injected problems.

**Why the warm-up run is excluded.** In two separate fresh environments the first customers
run was much slower than the following ones (57.72 s and 53.81 s, against 22–33 s). Memory
was the same, so the extra time is not extra work. The likely cause is the first loading of
newly installed libraries (for example while security software scans them), but this was
not proven. The warm-up runs are listed above; they are only excluded from the medians.

Output sizes (customers run 1): cleaned CSV 8,209,305 bytes, quarantine 192,777, removed
rows 113,542, JSON report 10,613,078, Markdown report 13,628. Orders run 1: cleaned XLSX
3,940,713 bytes, quarantine 50,307, removed rows 57,308, JSON report 4,919,056, Markdown
report 12,579.

## Earlier series and variability between sessions

The same datasets were measured on the same machine in three sessions:

| Series | Code | Customers median (range) | Orders median (range) | Orders peak working set |
| --- | --- | --- | --- | --- |
| Stage 7B | before Excel-formula detection was added | 31.45 s (31.08 – 33.27) | 117.53 s (115.34 – 117.82) | 517.3 MiB |
| Intermediate (superseded, not verified independently) | formula detection, first version | 22.91 s (22.18 – 53.81) | 82.49 s (80.28 – 83.60) | 565.9 MiB |
| Final | as published | 31.96 s (31.88 – 33.07) | 125.64 s (119.37 – 126.27) | 517.4 MiB |

Customers peak working set: 331.6, 331.8 and 331.8 MiB respectively.

- **Time varies much more between sessions than between runs of one session.** Within a
  series the range is 2–7 % of the median (excluding first runs), but between sessions the
  medians differ by about 30 % (orders: 82 s versus 118–126 s), in both directions,
  independently of the code. Timings from different sessions must therefore not be compared
  to judge a code change; only a large, repeated difference would be meaningful.
- **Memory is stable** (within about 2 MiB across all runs of a series), so memory changes
  between versions can be measured reliably.

### Memory effect of the formula-detection fix

The first version of the Excel formula scan released parsed cells but kept them attached to
their rows, which raised the orders peak by about 48 MiB. To compare versions without the
session effect, the three installed versions were run **back to back in one session on the
same file** (one run each):

| Version | Peak working set | Peak committed | Time (single run, not comparable) |
| --- | --- | --- | --- |
| Stage 7B code (no formula scan) | 517.8 MiB | 849.1 MiB | 63.12 s |
| Formula scan, first version | 566.2 MiB | 897.3 MiB | 77.57 s |
| Final code | 518.4 MiB | 849.7 MiB | 88.56 s |

The fix removes the extra memory: the final code is within 1 MiB of the original. The times
of these single runs rose in the order they were run and are much shorter than the same-day
series, so they show machine drift and are **not** evidence about the speed of each version.
Measured in isolation on the 100,000-row workbook, the formula scan itself takes about 2–3 s.

## Independent verification

[`scripts/benchmark/verify_outputs.py`](../scripts/benchmark/verify_outputs.py) does not import
the toolkit; it reads the files with `csv` and `openpyxl` and compares them with the
generator's manifest and with its own re-derivation of each configured rule. For each run it
checks:

- the input file's SHA-256 against the value recorded at generation, and the fingerprints in
  the report;
- cleaned + removed + quarantined = input rows, and the exact expected counts;
- headers of the three output files and the dimensions reported;
- that the removed rows are exactly the injected copies, each identical to the row it names;
- quarantine reasons, failures per validation rule, total issues and distinct rows affected,
  conversion failures per column, key-duplicate groups;
- **every value of every kept row** (identifiers keep their leading zeros, ambiguous dates and
  timestamps are unchanged, amounts and labels are normalized as configured) and, for the
  Excel output, the cell types (prices numeric; IDs and quantities text).

Results: 6/6 runs passed (1,032 and 1,031 checks per run, 0 failures). The verifier was
itself tested on deliberately altered outputs (an ID stripped of its leading zeros, a
quarantine row deleted, a rule count changed): all three alterations were detected. The
cleaned customers CSV was byte-identical across all runs, including the warm-up and the
Stage 7B series.

Protections also exercised on the 100,000-row files (Stage 7B): a second run without
`--overwrite` was refused with the existing outputs unchanged; using the input as output was
refused even with `--overwrite`; a column-name collision stopped the run with a failure report
and no data file.

## Limitations

- One machine, Windows 11 only; three measured runs per workflow per series.
- One file size (100,000 rows). No scaling behaviour is established; do not extrapolate
  linearly to larger files.
- No per-phase timing: the XLSX workflow is about 4 times slower than the CSV workflow, but
  how much of that comes from loading, verifying or writing workbooks was not measured.
- Large session-to-session variation in time (about 30 %), and slow first runs in a new
  environment.
- The JSON report lists every issue: about 10.6 MB for the customers file with about 30,000
  issue occurrences.
- Synthetic data with a high defect rate (about 14 % of customers rows and 10 % of orders
  rows fail at least one validation rule); real files may behave differently.
- No macOS, Linux or other Python versions were measured.

## Reproducing

From the project root, with the package installed, and a working folder outside the
repository (the data and outputs take about 95 MB):

```powershell
python scripts/benchmark/generate_data.py ..\dct-benchmark
python scripts/benchmark/measure.py
python scripts/benchmark/run_benchmark.py ..\dct-benchmark --repeats 3 --warmup
python scripts/benchmark/verify_outputs.py ..\dct-benchmark customers 1
python scripts/benchmark/verify_outputs.py ..\dct-benchmark orders 1
```

See [`scripts/benchmark/README.md`](../scripts/benchmark/README.md) for details.
