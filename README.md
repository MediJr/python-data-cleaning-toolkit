# Python Data Cleaning Toolkit

Rule-based cleaning of CSV and Excel (`.xlsx`) files, with a verified output file and a
report that lists every change, every value that could not be fixed safely, and every
validation failure.

> **Status:** personal portfolio project, version 0.1.0. It is tested (automated test
> suite plus independent verification of the sample outputs) but it is not a
> production-certified product and has not been used for a real client. Tested on
> **Windows 11 with Python 3.14.7 only** (see [Tested environment](#tested-environment)).

## The problem it solves

Spreadsheets exported from different systems rarely agree with each other: `NEW YORK`,
` new york` and `NYC` in the same column, dates written as `15/03/2024` in one row and
`03/15/2024` in the next, `N/A` mixed with empty cells, amounts such as `$950` or
`1,200.50`, customer IDs whose leading zeros disappear when the file is opened in Excel,
and duplicate rows.

Fixing this by hand is slow and hard to audit. Fixing it with a quick script is fast but
risky: a script can silently turn `03/04/2024` into the wrong month, replace missing
amounts with `0`, delete a row that was a legitimate second order, or overwrite the
original file.

This toolkit applies **explicit, written rules** and produces:

- a cleaned file that is reopened and compared with the data in memory before it is kept;
- the rows it removed and the rows it set aside (quarantine), each with the reason;
- a Markdown report for people and a JSON report for programs, listing what changed, what
  could not be fixed safely, and which validation rules failed.

Anything that would require a guess (an ambiguous date, a number in an unexpected format,
a possible typo, a suspicious value) is **left unchanged and reported**, so that a person
can decide.

### Intended users

- Someone who receives a messy CSV/XLSX export and needs a clean, documented version.
- A freelancer or analyst who must show a client exactly what was changed and why.
- A reviewer who wants to see how the cleaning decisions were made.

It works on ordinary tabular files that fit comfortably in memory. It is a command-line
tool; no programming is needed to change the cleaning rules (they live in a JSON file).

## Features

| Area | What it does |
| --- | --- |
| Reading | `.csv` (encoding and delimiter detection, with warnings) and `.xlsx` (sheet selection). Every cell is read as text, so nothing is converted by accident. Malformed files (rows with the wrong number of fields, broken quoting, duplicate column names, empty files) are rejected with the line number. Excel formulas are read as the value Excel last saved; formulas that have no saved value (workbooks generated by a program and never recalculated) are counted, reported as an anomaly and never silently treated as ordinary empty cells. |
| Profiling | `profile` command: rows, columns, what each column looks like, missing values, exact duplicates, values with leading zeros, ambiguous dates, stray spaces. Read-only. |
| Column names | Trim spaces, optional `snake_case`, explicit renames. Two columns that would get the same name stop the run instead of being merged. |
| Missing values | Empty and whitespace-only cells, plus tokens you list (`N/A`, `NULL`, ...). Values are **never filled in**; `0` and `unknown` are not treated as missing unless you say so. |
| Text | Trim, collapse repeated spaces, optional lower/upper/title case, per column. |
| Categories | Explicit mappings only (`NYC` → `New York`). Unmapped labels are listed, never merged automatically. |
| Dates | Input formats are listed explicitly; output is ISO `YYYY-MM-DD` by default. A value that matches two formats with different results (e.g. `03/04/2024`) is reported as **ambiguous** and left unchanged; impossible dates (`2024-02-30`) are reported. |
| Numbers | Decimal and thousands separators are configured explicitly; currency symbols are removed only if listed. Values with leading zeros (`007`) are refused because converting them would lose information. |
| Duplicates | Exact duplicates and duplicates on key columns are **detected**; they are removed only when you ask, and removed rows are saved with the row they duplicated. |
| Validation | Required columns, non-missing values, types, allowed values, numeric ranges, date ranges, regex patterns, uniqueness. Each rule either reports or quarantines rows; nothing is deleted. |
| Output | `.csv` or `.xlsx`. Written to a temporary file, reopened and compared cell by cell, then moved into place. In Excel output, codes stay text (`00123`) and fully converted numbers become numeric cells. |
| Reports | Markdown + JSON: execution status, data-quality status, dimensions, changes, conversion failures, duplicates, validation, warnings, input fingerprint. |

## Installation

Requirements: Python 3 (tested with 3.14.7) and `pip`. Commands below are for Windows
PowerShell, run from the project folder.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install .
```

To run the tests as well, install the development extra instead:

```powershell
python -m pip install -e ".[dev]"
```

If PowerShell refuses to run `Activate.ps1` ("running scripts is disabled on this
system"), either allow scripts for the current window only with
`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`, or skip activation and call
the environment's programs directly, e.g. `.venv\Scripts\python.exe -m pip install .` and
`.venv\Scripts\data-clean.exe --version`.

On macOS/Linux the equivalent activation command is `source .venv/bin/activate`
(not tested).

`requirements.txt` and `requirements-dev.txt` list the same dependencies as
`pyproject.toml` (a test keeps them identical). Runtime dependencies are only **pandas**
and **openpyxl**.

If Windows reports `DLL load failed ... blocked by an application control policy` when
importing numpy, see [Troubleshooting](docs/limitations.md#windows-application-control-blocking-numpy).

## Quick start

The repository contains synthetic sample files, so every command below can be run as is.
Both entry points are equivalent: `data-clean ...` (installed command) and
`python -m data_cleaning ...`.

```bash
data-clean --version
```

```bash
python -m data_cleaning --version
```

Both print `data-clean 0.1.0`.

**1. Profile a file (read-only):**

```bash
data-clean profile data/sample/customers_raw.csv --config config/customers_config.json
```

Excerpt of the output:

```text
- Rows: 15, columns: 8
- Missing cells: 5 (empty, whitespace-only, or one of ['N/A', 'NULL'])
- Exact duplicate rows (extra copies): 1

| Column | Looks like | Missing | Distinct | Flags | ...
| Customer ID | integer | 1 | 12 | 14 with leading zeros | ...
| Signup Date | mixed | 0 | 14 | 1 ambiguous dates | ...
```

**2. Clean a CSV file:**

```bash
data-clean clean data/sample/customers_raw.csv output/customers_clean.csv --config config/customers_config.json
```

```text
Execution: SUCCESS
Data quality: ISSUES FOUND - Execution succeeded, but 11 type(s) of unresolved issue (22 occurrence(s)) remain. Review them before using the data.
Rows: 15 -> 11 (removed 1, quarantined 3); columns: 8 -> 8
Wrote cleaned: output/customers_clean.csv (11 rows, verified)
Wrote quarantine: output/customers_clean_quarantine.csv (3 rows, verified)
Wrote removed_rows: output/customers_clean_removed_rows.csv (1 rows, verified)
Report: output/customers_clean_report.json
Report: output/customers_clean_report.md
6 warning(s); see the report.
```

The exit code is `3`: the run succeeded, but the data still has issues that a person must
review (this sample contains them on purpose).

**3. Clean an Excel sheet into an Excel file:**

```bash
data-clean clean data/sample/orders_raw.xlsx output/orders_clean.xlsx --sheet Orders --config config/orders_config.json
```

**4. The same with the module entry point, without a configuration file:**

```bash
python -m data_cleaning clean data/sample/customers_raw.csv output/customers_defaults.csv --drop-exact-duplicates
```

```text
Execution: SUCCESS
Data quality: NO RULES CONFIGURED - No validation rules were configured, so the data was not checked against acceptance criteria. The built-in checks found no unresolved anomalies.
Rows: 15 -> 14 (removed 1, quarantined 0); columns: 8 -> 8
Wrote cleaned: output/customers_defaults.csv (14 rows, verified)
Wrote removed_rows: output/customers_defaults_removed_rows.csv (1 rows, verified)
...
```

Without a configuration only safe defaults apply (see
[Behaviour without a configuration](#behaviour-without-a-configuration)). The exit code
is `0`, but the status says explicitly that nothing was validated.

Running a `clean` command a second time with the same output fails on purpose (the
files already exist); add `--overwrite` to replace them.

- Kept as is: `000102`, `00501` (identifiers keep their leading zeros), the name
  `ben okafor` (changing the case of names is not safe in general).

## Commands

| Command | Purpose |
| --- | --- |
| `data-clean profile INPUT [options]` | Describe a file without changing anything. `--report-dir DIR` also writes `INPUT_profile.json` and `.md`. |
| `data-clean clean INPUT OUTPUT [options]` | Apply the rules, write the verified output, companion files and reports. |
| `data-clean --help`, `data-clean clean --help`, `data-clean profile --help` | Full option list with examples. |

Options of `clean`:

| Option | Meaning |
| --- | --- |
| `--config FILE` | JSON cleaning configuration ([reference](docs/configuration.md)) |
| `--sheet NAME` | Worksheet of an `.xlsx` input (default: first sheet, with a warning if there are several) |
| `--encoding NAME` | Encoding of a `.csv` input (default: UTF-8, otherwise Windows-1252 with a warning) |
| `--delimiter CHAR` | Delimiter of a `.csv` input (default: detected among `, ; TAB \|`; `\t` for tab) |
| `--drop-exact-duplicates` | Remove rows identical in every column (first occurrence kept) |
| `--report-dir DIR` | Where to write the reports (default: next to the output) |
| `--overwrite` | Allow replacing existing output and report files (never the input) |
| `-v`, `--verbose` | Progress messages (placed before the command: `data-clean -v clean ...`) |

`profile` accepts `--sheet`, `--encoding`, `--delimiter`, `--config`, `--missing-token`
(repeatable), `--report-dir` and `--overwrite`.

## Output files

For `data-clean clean INPUT out/result.csv`:

| File | Written when | Content |
| --- | --- | --- |
| `out/result.csv` | the run succeeds | Cleaned data, reopened and verified before being kept |
| `out/result_quarantine.csv` | a rule with `"action": "quarantine"` failed | Rows set aside, with a `quarantine_reason` column |
| `out/result_removed_rows.csv` | duplicates were removed | Removed rows, with a `removal_reason` column naming the row that was kept |
| `out/result_report.md` | always (also when the run fails after reading the input) | Human-readable report |
| `out/result_report.json` | always (same) | Machine-readable report |

Companion files use the same format as the output (`.csv` or `.xlsx`). Row numbers in
reasons and reports are the line numbers of the CSV input (header = line 1) or the row
numbers of the worksheet.

## Configuration

Rules are written in a JSON file. Every key is optional; unknown keys and invalid values
are **rejected** (a typo never silently disables a rule). Column names in the rules refer
to the names **after** column-name normalization.

```json
{
  "column_names": {"style": "snake_case"},
  "missing_values": {"tokens": ["N/A", "NULL"]},
  "text": [{"columns": ["full_name", "city"], "collapse_whitespace": true}],
  "categories": [{"column": "city", "case_insensitive": true, "mapping": {"nyc": "New York", "new york": "New York"}}],
  "dates": [{"column": "signup_date", "formats": ["%Y-%m-%d", "%d/%m/%Y"]}],
  "numbers": [{"column": "annual_spend", "thousands": ",", "strip_chars": "$"}],
  "duplicates": {"remove_exact": true, "key_columns": ["customer_id"]},
  "validation": [
    {"id": "id_present", "rule": "not_null", "column": "customer_id", "action": "quarantine"},
    {"id": "spend_non_negative", "rule": "range", "column": "annual_spend", "min": 0}
  ]
}
```

Complete examples: [config/customers_config.json](config/customers_config.json) and
[config/orders_config.json](config/orders_config.json). Every key, its default and the
processing order are documented in [docs/configuration.md](docs/configuration.md).

### Validation and quarantine

Validation rules never change values. Each rule has an `action`:

- `"report"` (default): the row stays in the output and the failure is listed in the report;
- `"quarantine"`: the row is moved to the `_quarantine` file with the reason.

There is deliberately no "delete" action. Missing values are only checked by `not_null`;
the other rules ignore them so that "missing" and "invalid" are counted separately. One
row can fail several rules, so the report gives both the number of failures and the number
of distinct rows affected.

### Behaviour without a configuration

With no `--config` (or an empty `{}`), the tool only: trims column names, treats empty and
whitespace-only cells as missing, detects (but keeps) exact duplicates, and writes the
verified output and reports. It converts no dates or numbers and changes no text values.

Because no validation rules exist, the data-quality status is **`no_rules_configured`**
and the exit code is `0` if no built-in anomaly (such as kept duplicates) was found. This
means "nothing was checked against acceptance criteria", **not** "the data is valid".
Configure validation rules to get a meaningful `accepted` / `issues_found` status.

## Exit codes and statuses

| Exit code | Meaning |
| --- | --- |
| `0` | Success, and no unresolved issue (status `accepted` or `no_rules_configured`) |
| `1` | Error: invalid input, configuration or output path, or the run failed |
| `2` | Invalid command-line usage |
| `3` | Success, but unresolved data-quality issues remain (status `issues_found`) |

Every report shows two separate statuses:

- **Execution:** `success` or `failed` (a failed run writes a report saying which files
  were and were not produced).
- **Data quality:** `accepted` (all configured rules passed and no anomaly), `issues_found`,
  `no_rules_configured`, or `not_assessed` (execution failed).

A successful execution is never presented as proof that the data is clean.

## How the original data is protected

- The input file is opened read-only. Its SHA-256 fingerprint is computed before and after
  the run and recorded in the report; a difference makes the run fail.
- The input file can never be used as an output or report path, even with `--overwrite`.
- Before any processing, every file the run may write is checked. If any already exists
  and `--overwrite` was not given, the run stops and writes nothing.
- Files are written to a temporary file, verified by reopening, then moved into place, so
  an interrupted or failed export does not leave a half-written file under the final name.
- Removed and quarantined rows are saved, not discarded.
- Files from an earlier run that this run does not produce (e.g. an old `_quarantine`
  file) are left untouched and mentioned in a warning, never deleted.

## Errors

Expected problems produce one clear message and exit code `1`, for example:

```text
Error: ragged_rows.csv: the header has 3 fields but 1 row(s) do not: line 3 (2 fields). Check the delimiter and quoting.
Error: Unknown key(s) in configuration: missing_value. Allowed: categories, column_names, dates, description, duplicates, ...
Error: Sheet 'Nope' not found in orders_raw.xlsx. Available sheets: Read me, Orders
```

Running the same `clean` command twice without `--overwrite` (Windows output shown):

```text
Error: Planned output files cannot be written:
  - Output file already exists: output\customers_clean.csv. Choose another name or allow overwriting explicitly (--overwrite).
  - Output file already exists: output\customers_clean_quarantine.csv. Choose another name or allow overwriting explicitly (--overwrite).
  ...
```

If a problem occurs after the input has been read, the run fails with exit code `1` and a
report is still written:

- a cleaning step fails (for example a configured column that does not exist, or a
  column-name collision): no data file is written;
- an export fails after the cleaned file was written (for example the quarantine file
  cannot be created): the report lists exactly which files were written and marks the
  execution as failed, so those files must not be used.

An unexpected internal error is recorded in the report and then re-raised with its full
traceback; it is never hidden.

## Scope

Included: CSV and XLSX input/output, the cleaning operations and validation rules listed
above, reports, a command-line interface.

Not included (by design, for this version): legacy `.xls`, macro-enabled `.xlsm`, `.xlsb`
and `.ods` files (rejected with a message); several sheets or interdependent sheets in
one run; databases, APIs, web scraping, scheduling and cloud deployment; imputation of
missing values; fuzzy matching of categories; files too large for memory.

## Known limitations

- Tested only on Windows 11 with Python 3.14.7; Python 3.11-3.13, macOS and Linux are untested.
- One worksheet per run; `.xls`, `.xlsm`, `.xlsb` and `.ods` are not supported.
  Password-protected workbooks have not been tested.
- Whole files are loaded into memory. Measured: 100,000 rows take about 0.3-0.5 GiB of RAM
  (see [Performance](#performance)); larger files have not been measured.
- Dates are written as ISO text, not Excel date cells; scientific notation is not parsed.
- The JSON report lists every individual issue, so it grows with the number of anomalies
  (about 10 MB for 100,000 messy rows).
- With no validation rules configured, the status is `no_rules_configured` (exit code 0),
  which means "not checked", not "valid".

The complete list is in [docs/limitations.md](docs/limitations.md).

## Performance

Measured on one Windows 11 laptop (AMD Ryzen 5 7535HS, 13.7 GB RAM, NVMe SSD) with
synthetic files of 100,000 rows, through the installed `data-clean` command, three runs each
after a warm-up run:

| Workflow | Median time | Peak RAM (working set) |
| --- | --- | --- |
| Customers CSV → CSV (10 validation rules) | 31.96 s | 331.8 MiB |
| Orders XLSX → XLSX (5 validation rules) | 125.64 s | 517.4 MiB |

Every output was checked by an independent verifier (0 failures in 6 runs). Times varied by
about 30 % between sessions on the same machine, Excel files are about 4 times slower than
CSV, and no other size, machine or operating system was measured. Method, all individual
results, variability and limitations: [docs/performance.md](docs/performance.md).

## Architecture

The package is organised around a fixed pipeline; each step is a separate, tested function
that returns the new data plus a record of what it changed:

```text
check output paths ─► fingerprint + read input (all text) ─► profile
  ─► column names ─► missing values ─► text ─► categories ─► dates ─► numbers
  ─► exact duplicates ─► key duplicates ─► validation ─► quarantine
  ─► write + reopen + verify outputs ─► profile result ─► re-check input fingerprint
  ─► JSON + Markdown reports
```

Module responsibilities and design decisions are described in
[docs/architecture.md](docs/architecture.md).
